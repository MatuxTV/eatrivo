## 5. Recipe photos pipeline (uncommitted)

**Decisions:**
- separate photo table
- every generated recipe becomes an official recipe with a photo
- one image, auto-approved
- realistic top-down style
- public R2 URL
- costs kept low

**Database** (`src/db/schema.ts`, already pushed with `npm run db:push`):
- `recipe_images`:
  - `id`, `recipe_id` (FK, on delete cascade), `storage_key` (unique)
  - `status` (`pending | ready | failed`), `source` (`ai | admin | upload`)
  - `model`, `prompt`, `dish_signature` (indexed)
  - `width`, `height`, `bytes`, `error`, timestamps
- `recipes.cover_image_id`: FK to the image that is shown (on delete set null).
- `recipes.dish_signature` (indexed; **needs one more `db:push`**, see the checklist).
- The legacy `recipes.image_key` is kept. `ensureRecipeImage` adopts it for free.

**Pipeline** (`src/lib/recipe-images/`):

| File | What it does |
|---|---|
| `config.ts` | Model (`RECIPE_IMAGE_MODEL`, default `gemini-2.5-flash-image`), monthly budget (`RECIPE_IMAGE_MONTHLY_BUDGET_USD`, default 10), price table |
| `prompt.ts` | One fixed realistic top-down prompt |
| `signature.ts` | Dish signature: normalized English name + ingredient keys |
| `provider-core.ts` / `provider.ts` | Gemini REST via `GOOGLE_AI_API_KEY`, 60 s timeout, one retry on 429/5xx |
| `storage.ts` | `sharp` → WebP 1024 + 512 → R2 with an immutable cache header |
| `budget.ts` / `budget-store.ts` | Monthly spend in Upstash (micro-USD) + per-recipe lock |
| `urls.ts` | Image URLs built on the server from `RECIPE_IMAGE_BASE_URL` |
| `service.ts` | `ensureRecipeImage(recipeId)`, see below |
| `backfill.ts` | Batch runner shared by the admin endpoint, the cron and the script |

`ensureRecipeImage(recipeId)` takes the first step that applies:
1. A cover already exists → stop.
2. The recipe has a legacy `image_key` → adopt it.
3. The same dish already has a ready image → reuse it.
4. 2 or more failed attempts → skip.
5. The monthly budget is reached → skip.
6. Otherwise generate, store, and set the cover.

**Triggers:**
- **Every Rivo generation:** `persistGeneratedRecipesInBackground` (`src/lib/custom-recipes/auto-persist.ts`) persists the pantry and almost-cookable recipes, then generates their photos inside `after()`.
- **Save / cook:** `/api/recipes/custom/accept` makes sure the recipe has a photo.
- **Admin import:** a newly uploaded photo replaces the cover; otherwise one is generated.
- **Nightly cron** `/api/cron/recipe-images` at 02:30: up to 20 recipes per run, within the budget.
- **Admin endpoint:** `POST /api/admin/recipe-images/backfill?limit=3&source=catalog&dryRun=true`.
- **Local script:** `npm run db:backfill:recipe-images -- --limit=3 --dry-run`. It needs the `CLOUDFLARE_*` variables, which are only configured on Vercel today.

**UI:** `BasicHomeRecipePreview` gains `imageUrl` and `imageThumbUrl`, filled by `browse.ts`, `recipe-matches.ts` and the home loaders.
- Recipe cards and Uvaríš hneď use the thumbnail; Tip dňa and the sheet use the full size.
- The emoji tile stays as the fallback.
- `next/image` is used with `unoptimized`, since the files are already sized.

**Cost** (third-party price listings, checked 2026-10-22; verify on ai.google.dev):

| Item | Cost |
|---|---|
| Nano Banana | about $0.039 per image live, $0.0195 batch |
| Library backfill (87 recipes) | about $3.40 live |
| New AI recipe | about $0.04, limited by deduplication and the monthly budget |
| FLUX schnell (fallback if volume grows) | about $0.003 per image |

**Hosting:** `eatrivo.sk` DNS is at Websupport, so an R2 custom domain (`images.eatrivo.sk`) needs the DNS moved to Cloudflare. Use the r2.dev public URL for beta.

## 6. Beta audit (2026-10-22)

| # | Severity | Finding | Resolution |
|---|---|---|---|
| 1 | High | Every Rivo generation saves up to 2 public recipes; the same dish from different users was stored again and again. | **Fixed.** `persistAcceptedCustomRecipe` checks `recipes.dish_signature` and returns the existing recipe (any user or the catalog) instead of inserting a copy. Catalog recipes get their signature when they get a photo. AI recipes stay visible to everyone, deduplicated, per the product decision. |
| 2 | High | Persisting and generating the photo run inside `after()` within the same function lifetime; `generate` had `maxDuration = 60`, so the photo could be cut off. | **Fixed.** `generate` is 300 s, `accept` is 120 s, admin import is 300 s. |
| 3 | Medium | A recipe whose upload fails after a paid generation would be retried, and paid for, every night. | **Fixed.** Skipped after 2 failed attempts (`too-many-failures`). Fix it with an admin photo upload. |
| 4 | Low | The new cron route accepted `Bearer undefined` if `CRON_SECRET` was missing. | **Fixed** in `/api/cron/recipe-images`. The three older cron routes still use the same pattern (follow-up). |
| 5 | Low | `scripts/` is git-ignored, so `scripts/backfill-recipe-images.ts` would not be committed. | **Open.** Commit it with `git add -f`. The admin endpoint works without it. |
| 6 | Info | Budget counter race under parallel generation. | Accepted. Possible overspend of a few cents. |
| 7 | Info | `sharp` on Vercel. | OK. The lock file contains the `@img/sharp-linux-x64` binaries. |
| 8 | Info | `RECIPE_IMAGE_BASE_URL` missing. | OK. Placeholders are shown and nothing crashes. |

**Known gaps (not blocking beta):**
- Rivo **chat** recipes use a different flow. They are not auto-persisted and get no photo until someone bookmarks them.
- Profile → Saved recipes does not show photos yet.
- AI recipes are public: add a sentence about the shared recipe catalog to the terms.
- There are no unit tests for `ensureRecipeImage` or for the dedup in persistence, because both need the DB, Redis and R2. They are verified manually (below).

**Checks:**
- `npx tsc --noEmit`: clean
- ESLint on the changed areas: clean
- `npm test`: 400 pass, 1 fail. `validateRecipeJson accepts available preferences-only candidates` was already failing before these changes.
- `npm run build`: compiles

## 7. Checklist before publishing to beta

1. `npm run db:push`: adds `recipes.dish_signature` and its index. Additive only.
2. Vercel (beta) env:
   - `RECIPE_IMAGE_BASE_URL` (the `pub-…r2.dev` URL)
   - `GOOGLE_AI_API_KEY`
   - `CLOUDFLARE_S3_ENDPOINT`, `CLOUDFLARE_ACCESS_KEY`, `CLOUDFLARE_SECRET_KEY`, `CLOUDFLARE_S3_BUCKET`
   - `CRON_SECRET`
   - optional: `RECIPE_IMAGE_MONTHLY_BUDGET_USD`, `RECIPE_IMAGE_MODEL`
3. In the R2 bucket, enable the Public Development URL.
4. Commit, including `git add -f scripts/backfill-recipe-images.ts`, and deploy.
5. As admin: `POST /api/admin/recipe-images/backfill?limit=3&dryRun=true`, then without `dryRun`. That is about $0.12; review the 3 images. Then run the library in batches (`limit=50`).
6. Generate a recipe with Rivo:
   - within about 20 s it should appear with a photo in "Všetky recepty" for a second account
   - generating the same dish again must not create a new recipe or a new image
7. Smoke test on a phone:
   - Home: Tip dňa, Rivo button, the Uvaríš hneď swipe and Všetky/Zbaliť, the grid, bookmarks
   - the recipe sheet: red missing items, "Do nákupu (N)"
   - Profile saved recipes reload when reopened
   - the Rivo chat bookmark state
